# 回归稳定性复盘：为什么「改一处、跑全量」会陷入循环

> 复盘时间：2026-10-22　|　范围：2026-10-21 ~ 10-22 共 9 次全量尝试
> 结论先行：**这不是"修不完的 bug"，而是回归体系本身缺少三道防线**——时区基准、
> 环境隔离、判据强度。修复的是症状，体系缺陷没补，所以每轮都能"发现新问题"。

> **本轮收尾状态（2026-10-22 12:40）**：三项遗留的「高/中」待办已全部落地，
> 全量回归 **824 项 / 代码失败 0**，CI **4 个 job 全绿**（含新增的 F 类缺陷与
> 时间契约门禁）。这是多轮以来首次「本地全绿 + CI 全绿」同时成立。

> **⚠️ 阅读须知（2026-10-29 补记）**：本文是一次**历史复盘**，如实保留了当时的
> 状态与结论，因此正文中反复出现的 `tests/`、`tools/run_e2e.sh`、`e2e_framework.py`、
> 「824 项」等，描述的**都是 2026-10-22 的事实，现在这些都已不存在**。
>
> 2026-10-29 项目做了清理：`tests/` 整个目录与 `tools/run_e2e.sh` 已移除（原因与
> 代价见提交记录），CI 的 `e2e` job 一并删除，回归入口改为「五道静态门禁 +
> 导库建表冒烟 + 前端 vitest」。本文的**方法论仍然有效**（三道防线的诊断思路、
> 时区基准、环境隔离、判据强度），但**不要照着文中的命令去执行**。

## 一、失败序列复盘

### 1.1 九次全量尝试的完整轨迹

| # | 触发原因 | 结果 | 失败项 | 性质 |
|---|---|---|---|---|
| 1 | 首次全量（起点） | 805/811 | 6 | 真实缺陷 + 假失败混合 |
| 2 | 修 6 项后 | 808/809 | 1 | 假失败 |
| 3 | 修断言后 | 802/806 | 4 | 假失败（弱断言污染） |
| 4 | 修弱断言后 | 804/808 | 4 | 假失败（残留数据） |
| 5 | 清理残留 | 中断 | — | 环境（双进程） |
| 6 | 重跑 | 808/810 | 2 | 假失败（种子数量写死） |
| 7 | **提交 e2d9acb** | **811/811** | **0** | 本地首次全绿 |
| 8 | CI 上跑 | 失败 8 项 | 8 | **时区**（本地不可能复现） |
| 9 | 本次（时区修复后） | 737/737 + 21/21 | 0 | 但中途因环境中断两次 |

**关键事实**：第 7 次本地 811 全绿，第 8 次 CI 直接 8 项失败。**这 8 项在本地永远跑不出来**——这才是循环的真正来源。

### 1.2 失败之间的因果关系：三个独立病根，不是八个缺陷

CI 那 8 项失败看似分散，实际聚成 **3 个病根**：

```
病根 A：时间基准不一致（runner UTC vs 容器 Asia/Shanghai，差 8h）
  ├─ ★ 定时发布创建为草稿      → 期望草稿，实际已发布（+1h 变成 -7h）
  ├─ ★ 未开考学生取卷被拒      → 期望 403，实际 200
  ├─ ★ 未开考学生交卷被拒      → 期望 400，实际已截止
  └─ 连带 3 条下游：
       ├─ 学生交卷后进入待批改   → submission_id=None（前面根本没交成）
       ├─ AI 教学建议可调用      → 400（无提交记录）
       └─ 班级学情报告可生成     → 400（同上）

病根 B：用例判据与实际产品行为不符
  └─ ★ 跨年级学科 id 被拒 → 期望 403，实际 200
     后端 design 是"自动纠正到本年级同名学科"（review.py:219-223），
     这是**正确行为**，用例却只认"必须拒绝"。

病根 C：用例绕过统一入口自己拼地址
  └─ ★ SSE 接口可访问 → HTTP 401
     写死探测 8099/8080/8000，不读 BASE；跑在 8002 时连到另一个库的实例，
     本次登录的 Token 在那边无效。接口本身完全正常。
```

**结论**：8 项失败 = 1 个环境配置缺陷（A）+ 2 个测试判据缺陷（B、C）。
如果按"逐条修"，会改 8 处；按根因修，只需改 3 处。

### 1.3 更早的 6 项失败：同样是"一类"而非"六类"

前 6 次失败全部属于**测试自身缺陷**，没有任何一个产品 bug：

| 现象 | 真实原因 | 同类根因 |
|---|---|---|
| `年级列表 -> 10 个年级` | 写死 `len(grades)==9`（种子数） | **D：写死可变数量** |
| `班级列表 -> 5 个班级` | 写死 `len(classes)==4`（种子数） | D |
| `管理员可批量移出学生` PASS 但残留 | 弱断言 `len(sids)>=1` | **E：断言强度不足** |
| `[E2E-RS-] 导入测试班` 残留 | 上一条的后果 | E（连锁） |
| `AI 整理笔记` 同用例名出现两次 | 双进程共用同一 DB | **F：环境未隔离** |
| `删除笔记 -> 422` | 同上 | F |

**这三次循环（第 2→3→4→6 次）全部由 D/E/F 三个根因驱动**，与产品代码无关。

## 二、问题清单（按根因排序）

> 优先级定义：**P0** = 会让绿变红/红变绿，直接误导发布决策；**P1** = 显著拉长反馈周期；**P2** = 影响可维护性。

### P0-1　时间基准依赖宿主机时区（病根 A）

| 项 | 内容 |
|---|---|
| **根因** | `utcnow()` 名字是 UTC，实现却是 `datetime.now()`（本地时间）。整个系统的"当前时间"完全取决于**进程所在时区**。 |
| **影响范围** | 后端 69 处 `utcnow()` + 13 处直接 `datetime.now()`；涉及定时发布、考试时间窗、批改截止、Token 过期。 |
| **为何本地测不出** | 本地测试进程与容器同为 Asia/Shanghai，**差值恒为 0**，天然屏蔽。CI runner 是 UTC → 差 8 小时。 |
| **本可提前暴露** | 是。只要有一个用例断言"服务端返回的时间 ≈ 测试进程时间"，或在 UTC 环境下跑过一次。 |
| **修复** | ✅ 已做：`/health` 返回 `server_time`；测试统一 `server_now()`/`dt_str()`；`test_admin` 加契约断言。 |
| **遗留** | `utcnow()` 命名仍误导。建议改名 `now_local()` 或明确改为真 UTC 并全链路加时区。 |

### P0-2　测试绕过统一入口，自己拼服务地址（病根 C）

| 项 | 内容 |
|---|---|
| **根因** | `test_agent_struct.py` 写死 `for probe in ("...8099", "...8080", "...8000")`，不读 `E2E_BASE`。 |
| **影响范围** | 本次 1 条，但同类写法在 `tests/verify_*.py` 中还有 8 个孤立脚本。 |
| **为何本地测不出** | 本地通常开在 8000，恰好命中。换端口（隔离库、CI 自定义）立刻失效。 |
| **本可提前暴露** | 是。只要在非默认端口跑过一次，或做一次"硬编码地址"静态扫描。 |
| **修复** | ✅ 已做：改用 `from e2e_framework import BASE`。 |
| **遗留** | 8 个 `verify_*.py` 仍在体系外，未被 run_all 收录，不受任何门禁保护。 |

### P0-3　`ENV` 类用例不计入失败，退出码失真（病根 F 的放大器）

| 项 | 内容 |
|---|---|
| **根因** | `R.env()` 记 `status="ENV"`，`R.failed` 只统计 `"FAIL"`，`run_all` 又以 `return 0 if R.failed == 0`。**ENV 既不入总数也不入失败**。 |
| **影响范围** | 本次 737 项里有 9 条 ENV、尾段 21 项里 3 条 ENV。若关键前置全挂，可能"0 失败"但实际只跑了 200 项。 |
| **危险场景** | 服务宕机 → 用例走 `R.env` → 报告显示"通过 N 项、失败 0" → **门禁放行**。 |
| **本可提前暴露** | 是。应有"总用例数不得低于基线"的断言（如 < 800 即失败）。 |
| **实测验证** | 把 `E2E_BASE` 指向不存在的 9999 端口跑 admin：**退出码 0**，输出"共 1 项 / 通过 0 / 失败 0"。门禁完全失效。 |
| **修复** | ✅ 已做：ENV 计入总数并单列；新增三条硬门禁（见 R2.1）。修复后同一场景退出码变 1 并给出"零用例通过"提示。 |

> **本条是整轮复盘里性价比最高的发现**：它不影响任何用例的正确性，却能让
> "整套服务挂掉"伪装成"全部通过"。任何依赖 `run_all` 退出码的自动化
> （`auto_ship.sh`、CI 的 e2e job）此前都可能带着这个漏洞发布。


### P1-4　断言写死可变数量（病根 D）

| 项 | 内容 |
|---|---|
| **根因** | 把**种子数据量**当常量：`len(grades)==9`、`len(classes)==4`。但回归自己会建年级/班级（资源专项、建班审批流）。 |
| **影响范围** | `test_admin` 2 条，曾连续污染 3 轮。 |
| **为何本地测不出** | 干净库上偶尔绿；跑过几轮的库必然红。**取决于库的"年龄"**，而非代码。 |
| **已修复** | ✅ 改语义断言：`grade_num` 覆盖 1..9、种子班名子集判定。 |

### P1-5　断言强度不足，失败也绿（病根 E）

| 项 | 内容 |
|---|---|
| **根因** | `check("批量移出学生", len(sids) >= 1)` 只断言"有东西可动"；移出全部失败同样成立。 |
| **连锁危害** | 移出静默失败 → 班级删不掉（"仍有 2 名学生"）→ `[E2E-RS-] 导入测试班` 永久残留 → 污染下一轮的年级/班级计数 → **一个弱断言毁掉后面三轮**。 |
| **已修复** | ✅ 回读花名册断言 `removed == len(sids) and not left_imp`；禁止 `check(..., True, ...)`。 |
| **遗留** | 仍有 4 处 `check(..., True, ...)`（test_admin:157、test_learning:74、test_teacher:243/724/727），需逐个核查是否为合理的"信息性记录"。 |

### P1-6　阶段间强状态耦合，不能独立运行（病根 F）

| 项 | 内容 |
|---|---|
| **根因** | `test_student.py` 读 `R.context["task_id"]`（由 teacher 阶段写入）；`test_learning.py` 读 `R.context["stu_subject_id"]`。 |
| **影响** | 无法"只跑受影响阶段"，只能全量；单阶段跑会 KeyError 或用兜底数据导致语义漂移。 |
| **本可提前暴露** | 是。设计时就该让每个阶段能自建前置数据。 |
| **修复** | ⬜ 待做（见改进方案 R3）。部分已兜底（`R.context.get()` + 回退逻辑）。 |

### P1-7　回归环境未隔离，可被双进程污染（病根 F）

| 项 | 内容 |
|---|---|
| **根因** | 手动跑用开发库 `backend/data/edu_platform.db`，且 `TaskStop` 不保证 python 子进程退出。 |
| **本次后果** | 两个 `run_all.py` 共用同一 SQLite，互相踩数据；日志交错出现 `整�` 半截中文；`toggle` 被写锁阻塞 **15 小时**（误判为死锁）。 |
| **已缓解** | ✅ 改用独立数据目录 + 8002 端口；`auto_ship.sh` 本来就用 `mktemp -d`。 |
| **遗留** | 缺少"跑前检查残留进程"的自动门禁。 |

### P2-8　无 Python 静态检查与 pre-commit

- 无 `.pre-commit-config.yaml`、无 flake8/ruff 配置。
- CI 只有前端三项扫描（`scan_vue_refs`/`scan_vue_dup`/`check_data_data`），**后端零静态检查**。
- 后果：`BASE + "/api/v1/health"` 这类路径拼接错误（我本次亲手犯过）只能靠跑用例发现。

### P2-9　报告覆盖机制（已修）

- `run_all.py admin` 会把 811 项报告覆盖成 98 项。已改为单阶段写 `E2E_REPORT.partial.md`。

### P2-10　游离脚本未纳入门禁

- 8 个 `tests/verify_*.py` 不在 `run_all` 中，写死端口，从未被回归覆盖。

## 三、根因归并：三个体系缺陷

把 10 条问题按"为什么不早发现"归并：

| 体系缺陷 | 覆盖的问题 | 一句话 |
|---|---|---|
| **① 环境假设未显式化** | P0-1、P0-2、P1-7、P2-10 | 用例隐式假设"时区一致、端口是 8000、库是干净的、进程只有一个"。任一假设破了就红，且**本地恰好全都成立**。 |
| **② 判据强度不受控** | P0-3、P1-4、P1-5 | 断言可以弱到"恒真"，也可以硬到"写死种子数"。没有机制约束，靠人肉 review。 |
| **③ 反馈回路太长** | P1-6、P2-8 | 只能全量 35 分钟；后端无静态检查。错误要 35 分钟才发现，且一次只见一个面。 |

**这解释了循环**：①导致"本地绿、CI 红"，②导致"红的不一定是真 bug"，③导致"每次只能验证一件事"。三者叠加 → 改一处、等 35 分钟、发现另一处。

## 四、改进方案

### R1　环境契约显式化（治 ①）

**R1.1 服务端时间作为唯一基准（已落地）**
- `/health` 返回 `server_time`；测试统一 `server_now()`。
- **加固**：`test_admin` 断言 `server_time` 存在且格式合法（已加）。

**R1.2 启动自检：时区一致性探针**
在 `/health` 增加 `tz_offset_minutes`（服务端相对 UTC 的偏移），并在回归开头断言：
```
abs(server_offset - expected_offset) < 1min    # expected 从环境变量读，CI 设 +480
```
这样"容器时区配置错"会在第一条用例就炸，而不是等 8 条时间用例。

**R1.3 禁止硬编码地址（门禁化）** ✅ 已落地

`tools/check_hardcoded_host.py` 扫描 `tests/**/*.py`：
- 命中 `http://localhost:端口` / `127.0.0.1:端口` → **阻断**；
- 白名单：`e2e_framework.py`（它本身就是负责探测端口的）；
- `verify_*.py` 等 8 个历史脚本不在 `run_all` 体系内，降级为 WARN 不阻断
  （若将来纳入回归，须从 `LEGACY_FILES` 名单移除）。

**R1.4 回归强制独立数据目录** ✅ 已落地

新增 `tools/run_e2e.sh`，手动调试也走它，内部完成：
```
1. 检查残留 run_all.py 进程（有则先清理，避免双进程抢锁）
2. mktemp -d 建独立 DATA 目录
3. 自动选空闲端口（8001-8010）启动后端
4. 契约自检：/health 必须返回 server_time
5. 跑 run_all.py（透传阶段参数）
6. 退出时清理进程与临时目录（--keep 可保留）
```

**实测**：`run_e2e.sh agent_struct` 在自动选中的端口上 15/15 通过，
SSE 用例正常（证明 P0-2 修复有效）；`run_e2e.sh admin` 98/98 通过。


### R2　判据强度受控（治 ②）

**R2.1 `ENV` 计入总数并设下限（P0）** ✅ 已落地

改 `run_all.py`：
- 报告"总计" = PASS + FAIL + ENV，ENV 单列；
- 三条硬门禁，任一触发即退出码 1：
  1. `passed == 0` → 零用例通过（服务不可达的最强信号）
  2. `ENV 占比 > 5%` 且样本 ≥ 100 → 成片跳过
  3. 全量时 `passed < 730` → 阶段被跳过或中断

> 单独加"比例校验"是不够的：服务完全不可达时只有 1 条 ENV，样本不足
> 会跳过比例校验，反而放过。**必须先判 `passed == 0`**，这是实测发现的。


**R2.2 禁止弱断言（门禁化）** ✅ 已落地

`tools/check_weak_assertion.py`：
- `check(<name>, True, ...)` → 阻断，除非带 `# allow-info-only`（写在 `check(` 行或其上一行）；
- `check(..., len(x) >= 1, ...)` → 警告（若该对象随后被删除/清理，必须回读）。

**实测收益**：首次运行抓出 5 处恒真断言，其中 **2 处是真缺陷**：

| 位置 | 原写法 | 危害 |
|---|---|---|
| `test_teacher.py:727` | 报告生成**失败**分支也 `check(..., True, ...)` | 报告 500 被伪装成通过 |
| `test_teacher.py:739` | `p.get("success") or is_down(p) is False` | 逻辑等价于"服务可达即通过"，业务失败全绿 |

其余 3 处位于 `if success` 分支内，属信息性记录，已标注 `allow-info-only`。


**R2.3 语义断言替代数量断言**

已建立规范，写入 `tests/README.md`：
- ❌ `len(grades) == 9` 　✅ `{1..9} <= {g.grade_num}`
- ❌ `len(classes) == 4` 　✅ `seed_class_names <= {c.name}`
- ❌ `user_count == 51` 　　✅ 与创建前基准做差值

**R2.4 断言必须先"能红"再"能绿"**

新增用例时，必须在修复前跑一次确认它**确实失败**（防止写了个恒真断言）。

### R3　缩短反馈回路（治 ③）

**R3.1 阶段解耦：每个阶段自建前置数据**

改造要点：
- `test_student` 不再依赖 `R.context["task_id"]`；若无则**自建**一张卷 + 一个任务。
- `R.context` 仅作优化缓存，缺失时自动重建。
- 目标：任意阶段可单独运行（`run_all.py student` 独立跑通）。

**R3.2 分层验证（已加 `--stages`，需配套）**

`auto_ship.sh --stages auto` 已实现按影响半径选阶段。配套要求：
- 命中 `e2e_framework.py` / `models` / `core` / `services` / `frontend/src/utils` / `Dockerfile` → **全量**；
- 其余按 `api/v1/*` 映射业务阶段；
- 本地开发循环用单阶段（3~8 分钟），提交前用 `--stages auto`。

**R3.3 后端静态检查进 CI** ✅ 部分落地

```
python -m compileall -q backend/app                 # 已有
python tools/check_hardcoded_host.py                # 新增
python tools/check_weak_assertion.py                # 新增
```
后两项已接入 `ci.yml` 的 backend job 与 `auto_ship.sh` 第 0 步，
