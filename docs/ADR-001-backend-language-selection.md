# ADR-001：后端语言选型——是否从 Python 迁移到 Go

- **状态**：已决策（暂不迁移）
- **日期**：2026-11-02
- **决策者**：项目负责人
- **相关**：`docs/ARCHITECTURE_ASSESSMENT_2026-11.md`

---

## 背景

系统当前为 FastAPI（Python 3.11）单体，v2.2.19，后端 32,082 行 / 272 端点 / 49 表，单 worker + SQLite WAL 部署。提出评估「整体改用 Go + Gin/Echo 是否更合理、性能与资源占用是否显著改善」。

## 决策

**不迁移。** 保持 Python 后端，把同等投入用于数据库层与并发模型的优化。

## 依据

### 1. 实测基线（本地单实例，SQLite，无 LLM，无向量库）

| 场景 | 并发 | 吞吐 | p50 | p95 |
|---|---|---|---|---|
| `/health`（无鉴权、无 SQL） | 40 | **526 req/s** | 77 ms | 200 ms |
| 题目列表（鉴权 + 4 次 SQL） | 10 | 135 req/s | 59 ms | 142 ms |
| 题目列表（鉴权 + 4 次 SQL） | 40 | **120 req/s** | 268 ms | 556 ms |

- 单核 CPU 占用 1.14 核（GIL 下满负载只能吃满一核）。
- 空闲 RSS 149 MB，压测后 183 MB，峰值 201 MB（不含 chromadb/onnxruntime）。
- 并发 10 → 40 吞吐**不升反降**（135 → 120），p95 翻 4 倍 —— 典型的单进程队列饱和。

### 2. 瓶颈归因

每请求耗时拆解：`/health` 1.9 ms（框架 + JSON），题目列表 8.3 ms。
**框架开销占 23%，业务开销（4 次 SQL + 鉴权 + 序列化）占 77%。**

换成 Go，可优化的是那 23%：即便把框架开销归零，单请求仅从 8.3 ms 降到 6.4 ms，**提升上限约 23%**。SQL 执行时间与语言无关。

### 3. Go 的真实优势不是"每请求更快"，而是"能用多核"

Go 的 goroutine 模型可在多核上线性扩展，Python 受 GIL 限制只能吃满单核。
但 Python 有等价手段：`uvicorn --workers N`（多进程）。读密集场景下 4 worker 可拿到 3–4 倍（120 → 400+），**配置改动 1 行**。

而多进程的天花板不是 GIL，是 **SQLite 单写者**：写并发下 `busy_timeout=5s` 会把队列拖成 500。这个天花板换 Go 同样存在。

> 结论：Go 用 6–9 人月买到的 8 倍，用「PG + 4 worker + 权限缓存」2 周能买到 4 倍；剩余差距只在极端并发（>1000 同时在线）才有意义。

### 4. 资源占用

| 项 | 现状 | Go 版 | 差额 |
|---|---|---|---|
| 常驻内存 | 149–201 MB（无向量库）/ 生产含 ONNX 估算 400–550 MB | 60–80 MB | 省 100–350 MB |
| CPU | 压力下单核打满 | 可吃满多核 | 仅在 CPU 密集时兑现 |
| 镜像 | ~1.5 GB（python-slim + chromadb + langchain + nginx） | ~150 MB（静态二进制 + nginx） | 省 1.3 GB 磁盘 |

在 4 GB 内存的目标机上，省 100–350 MB ≈ 2.5%–9%，不足以支撑一次全量重写。

**注意**：若迁移到 Go，Chroma（嵌入式向量库）没有等价物，必须换成外部服务（qdrant/weaviate，+80–150 MB 独立进程）或改调外部 embedding API（新增网络依赖）。**内存净收益可能归零。**

### 5. 迁移成本与风险

| 模块 | 行数量级 | Go 难度 | 说明 |
|---|---|---|---|
| CRUD 端点（约 200 个） | ~15k | 中 | 机械翻译，量大；ORM 语义差异（SQLAlchemy → sqlc/GORM） |
| 组卷 / 判分 / 报表 | ~6k | 高 | 业务规则重写，回归风险最高 |
| 文档导出（docx/pdf/xlsx） | ~3k | **很高** | Go 生态弱：DOCX 需 unioffice（商业授权），PDF 中文排版与公式支持差 |
| AI Agent + RAG | ~4k | 中高 | LLM 调用简单；Chroma 需替换；prompt/降级逻辑重写 |
| 基础设施（JWT/熔断/锁/迁移/种子） | ~4k | 中 | 全部重写，包括 6 个已踩过的坑 |

合计：32k 行 Python → 约 45–55k 行 Go。按 250 行/人日（含测试）估算 **170–220 人日**，即单人 8–10 个月、双人 4–5 个月，且期间业务冻结或双栈并行。

**最贵的恰好是 Python 生态最强的三块**（中文文档生成、Excel 解析、向量检索），而它们都不是并发问题。

## 后果

- 保留现有技术栈，接受 120–135 req/s 的单进程上限。
- 该上限对当前规模（<300 同时在线）**够用但余量小**，须按下节路线图优化。
- 若未来触发复审条件，按「旁路服务」渐进迁移，不做整体重写。

## 复审触发条件（任一成立则重新评估）

1. 完成 PG + 4 worker + 权限缓存后，在线 > 1000 且 P95 仍 > 500 ms。
2. 需要单机维持 5000+ 长连接（WebSocket 实时监考 / 推送）。
3. 部署环境内存硬限制 < 256 MB（边缘设备 / Serverless）。
4. 出现持续 CPU 密集负载（批量 OCR、视频转码、大规模报表），且单次超过 1 s。
5. 团队有 ≥3 名 Go 工程师，且 Python 侧维护成为人力瓶颈。

## 替代路线（同等投入下的优先级）

| 优先级 | 动作 | 成本 | 预期收益 |
|---|---|---|---|
| P0 | 权限快照缓存（去掉每请求 4 次 SQL 中的 3 次） | 1 天 | +30–40% 吞吐 |
| P0 | 修 `GET /edu/subjects?distinct=true` 的 48.5 ms 异常（其余端点 4–5 ms） | 半天 | 该端点 10 倍 |
| P1 | `uvicorn --workers 2~4`（同步放大 healthcheck start-period） | 1 小时 | 读密集近线性 |
| P1 | AI 端点全部走 `/agent/jobs` + 全局信号量 | 1 周 | 消除 AI 拖累非 AI 接口 |
| P2 | SQLite → PostgreSQL | 2 周 | 解除单写者天花板 |

前三项合计约 2 天，可把有效吞吐从 120 提到 350–450 req/s —— 覆盖未来 2–3 年的规模增长。

## 备注：如果重来一次

若项目从零开始、目标明确为区县级（万级并发、多副本部署），Go + PG + Redis 是合理选择。
但当前已 32k 行、272 端点在跑、单人维护，重写的期望收益为负。
