### P0-1　改密后当前会话立即失效（"改密即自杀"）

**位置**：`backend/app/services/auth_service.py:276`｜`backend/app/api/deps.py:61-62`｜`backend/app/api/v1/auth.py:412-419`｜`frontend/src/views/Profile.vue:124-140`

```python

user.password = hash_password(new_password)
user.must_change_password = False
revoke_user_tokens(db, user.id)     # ← 吊销该用户的**全部**令牌，含调用者自己这个
db.commit()
```
```python
# deps.py:61-62（每次鉴权都查水位）
if is_user_token_revoked(db, payload):
    raise AuthException("密码已变更，请重新登录")
```
```python
# auth.py:412-419（改密接口不回签令牌）
auth_service.change_password(db, user, payload.old_password, payload.new_password)
return ok(message="密码修改成功")
```
```js

await authApi.changePassword({ old_password: ..., new_password: ... })
ElMessage.success('密码修改成功')
await loadProfile()        // ← 这一行必然 401 → 拦截器清 token → 跳登录页
```

**水位语义（已核实）**：`revoke_user_tokens` 写 `invalid_before_ts = time.time()`，`is_user_token_revoked` 用令牌 `iat` 与之比较 → **改密前签发的令牌一律作废**，改密后签发的有效。设计正确，但**改密接口用的正是改密前签发的那个令牌**。

**触发路径**：任何一次改密。**强制首次改密的账号（演示教师/学生、管理员重置的账号）走同一条路径**：登录 → `must_change_password=True` → 跳 `/profile` → 改密 → 令牌作废 → 401 → 被踢回登录页 → 用新密码再登一次。

**影响**：用户看到"密码修改成功"后紧跟"登录已过期，请重新登录"。安全上确实止了损，但**止损手段伤到了操作者自己**，且这是**每一次**密码修改的必经路径，不是边缘场景。

**修复**：`PUT /auth/password` 成功后**回签一对新令牌**（access + refresh），前端按刷新流程写回 localStorage。这样既保住"旧令牌全死"（止损成立），又不作废调用者自己。

### P0-2　补列失败阻断启动 → 容器 running 但全站 502

**位置**：`backend/app/core/db_migrations.py:379-388`｜`deploy/supervisord.conf:22-24`｜`docker-compose.yml:26,76-81`

```python
except Exception as exc:
    db.rollback()
    logger.error("结构迁移失败 %s.%s: %s", table, column, exc)
    raise RuntimeError(f"结构迁移失败：{table}.{column}: {exc}") from exc
```
```ini
[program:backend]
autostart=true
autorestart=true
startretries=5
```

**失效链（已逐环核实）**：
1. 迁移失败 → uvicorn 启动即退出；
2. supervisord 重试 5 次后把该 program 置 **FATAL 并停止重试**（supervisord 自身不退出）；
3. 容器 PID 1 仍是 supervisord → **容器不退出** → `restart: unless-stopped` 不生效；
4. nginx 照常运行并反代到 8000 → **全站 502**；healthcheck 失败只把容器标成 `unhealthy`，Docker 不会因此重启。

**注意**：这里不是"无限重启循环"，而是**"容器活着、站点全挂"**——从运维视角更隐蔽（`docker ps` 显示 Up，看不出是 FATAL）。

**触发条件**：DDL 对有数据的表不适用（如 NOT NULL 无默认值）、瞬时 `database is locked`、磁盘满。

**修复**：区分确定性错误（DDL 本身写错）与瞬时错误（locked / IO）——后者重试 3 次再决定；阻断时输出明确的"人工处理"指引（哪张表哪一列、怎么修），并让 backend FATAL 时 supervisord 一并退出容器，使 `restart: unless-stopped` 能真正接管自愈。

### P1-9　确认框点"取消"＝"页面运行时错误： cancel"——红色横幅永久盖住页头，全站 21 处中招

> **这条是靠登录后的实机走查才发现的**（管理员账号，1920×1080，2026-11-06）。代码层它一直存在，但只有真的点一次"取消"才会暴露。

**位置**：`frontend/src/views/admin/JobManage.vue:183`（`await ElMessageBox.confirm(...)` 无 try/catch）｜`frontend/src/main.js:24-26`（`isBusinessError` 白名单）｜`frontend/src/main.js:28-47`（`errorHandler` → 全屏红条）


**即：前端根本没发请求，什么业务都没发生，但整页像崩了一样。**

而且这条横幅是 `position:fixed; top:0; z-index:99999`（`main.js:42-43`），后果比一条报错提示严重得多：

1. **它盖住的是 60px 的页头**——logo、面包屑、通知铃、用户头像全部被遮住一半（实机截图确认：页头只剩底部约 15px 露出来）。

#### 根因链（4 步，每一步都可验证）

| # | 环节 | 事实 |
|---|---|---|
| 1 | Element Plus 行为 | `ElMessageBox.confirm()` 被取消时，promise **reject 字符串 `'cancel'`**（不是 Error 对象） |
| 2 | 组件层漏保护 | `JobManage.vue:183` 的 `await ElMessageBox.confirm(...)` 外面**没有 try/catch** |
| 3 | 框架层接管 | Vue 3 的 `callWithAsyncErrorHandling` 会把 async 事件处理函数的 rejection 交给 `app.config.errorHandler` |
| 4 | 白名单漏判 | `main.js:24-26` 的 `isBusinessError` 只认 `__handled` / `isAxiosError` / `err.response` 三种——`'cancel'` 一个都不匹配 → 被当成"前端崩溃" |

第 4 步是**本轮修复自己造出来的**：`main.js` 的全局错误捕获是这轮加的（注释写明"此前只会让内容区白屏、无任何提示"），方向正确，但它把"用户取消了一个确认框"也归类成了崩溃。

全站 `await ElMessageBox.confirm/alert` 共 **43 处**，其中 **21 处不在 try 块内**（用括号栈精确跟踪 `try/catch` 归属，已与 ripgrep 行号逐条对齐），分布在 **15 个文件**：

| 文件 | 行号 |
|---|---|
