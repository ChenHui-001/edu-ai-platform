### 最需要立刻处理的六件事

1. **P1-A　修 P1-1 时打开了账号枚举预言机（新增，P1）**——`/auth/forgot-password` 现在对**存在的账号**返回 `sent:false` + "当前未检测到可用的邮件配置"，对**不存在的账号**返回 `sent:true` + "若该账号存在，验证码已发送"。两者响应**可稳定区分**（已实测），攻击者用任意候选邮箱批量试即可判定该邮箱是否已注册。**修复前两者都是 `sent:true`，反而不可区分**——这是本轮修复动作**新引入**的暴露面。
2. **P1-C　演示题目的 `options` 写成了纯字符串数组，违反全站契约（新增，P1）**——造出来的 10 道演示题，`options` 是 `["A. -3", "B. 0", …]`，而全站契约是 `[{"key":"A","text":"-3"}]`。后果实测：试卷 **Excel 导出 500**（`TypeError: string indices must be integers`）、错题本**导出 500**（`AttributeError: 'str' object has no attribute 'get'`）、学生端答题页读 `o.key`/`o.text` 会渲染成 `undefined. undefined`——**P1-8 声称要"点得出来"的组卷/导出/答题链路，恰好就是被演示数据打挂的那几条**。

### P1-A　修 P1-1 时打开了账号枚举预言机（新增）

> **这条是本轮修复动作直接引入的新暴露面**，不是旧问题没修掉。

**位置**：`backend/app/api/v1/auth.py:537-567`（forgot-password）｜`frontend/src/views/login/Login.vue:222`

第二轮 P1-1 报的是"邮件未配置时仍谎报'已发送'"。本轮修法是：**邮件未配置且账号存在时，返回 `sent:false` 并明确提示"当前未检测到可用的邮件配置，请联系管理员重置密码"**（`auth.py:556-562`）。这是正确的——后端不再骗人。

**但同一个端点里，账号不存在走的是另一条分支**（`auth.py:551-553`）：

```python
if not user:
    # 安全考虑：不泄露账号是否存在
    return ok({"sent": True}, message="若该账号存在，验证码已发送")
```

两条分支的**响应体 `data.sent` 与 `message` 完全不同**——修复前两者都是 `sent:true`，**不可区分**；修复后**可稳定区分**。

**实测（本地演示库，给 admin 挂上真实邮箱，库中无 SMTP 配置）**：

```
【存在的账号】admin-real@example.invalid
   HTTP 200  data.sent = False
   message = 验证码已发送（若系统已配置邮件服务）。当前未检测到可用的邮件配置，请联系管理员重置密码

【不存在的账号】nobody-here@example.invalid
   HTTP 200  data.sent = True
   message = 若该账号存在，验证码已发送

响应可区分（=账号枚举预言机）: 是 ⚠
```

**后果**：攻击者拿任意候选邮箱批量打 `/auth/forgot-password`，用 `sent` 字段即可判定该邮箱/手机号**是否已注册**。本系统承载未成年人真实数据、且 `identity` 体系里有"学生/教师"的区分，邮箱枚举是**定向钓鱼与社工攻击的前置信息**。注意这条与上一轮 P2-9（无条件信任 `X-Real-IP`）叠加时更糟。

**修复**（三选一，推荐第一个）：

1. **两条分支返回完全相同的响应**——账号不存在与"存在但邮件未配置"都返回 `{"sent": true}` + 同一句文案，把"邮件未配置"这条运维信息**移到别处**（例如登录页的静态提示、或管理端"系统配置"页），绝不从匿名端点的响应里透出。
2. 若必须区分，则**只在 `sent` 字段上区分，message 完全一致**——但这仍泄露存在性，不推荐。
3. 收紧触发条件：仅当 `APP_ENV=production` 且已配置 SMTP 时才走"未配置"分支，其余一律按统一响应。

**顺带（同一处，P2 级）**：`Login.vue:222` 提示"（10 分钟内有效）"，而后端 `core/security.py:504` 的 `store_reset_code(..., ttl_seconds: int = 300)` 是 **5 分钟**。更讽刺的是**同一个文件 `:217` 的注释自己写着**"否则用户白等 5 分钟，下一步必然'验证码错误'"——注释说 5 分钟，文案写 10 分钟，自相矛盾。

### P2-A　`init_jobs` 的"自动停用存量未注册任务"是死代码（新增）

**位置**：`backend/app/services/init_db.py:459-461`

```python
for name, func_path, cron, desc in DEFAULT_JOBS:
    exists = db.scalar(select(ScheduledJob).where(ScheduledJob.name == name))
    if not exists:
        if func_path not in JOB_HANDLERS:
            continue
        db.add(ScheduledJob(...))
    elif func_path not in JOB_HANDLERS and exists.is_active:   # ← 这里
        exists.is_active = False
        logger.warning("定时任务「%s」的执行逻辑未注册，已自动停用", name)
```

`func_path` 是**循环变量**（来自 `DEFAULT_JOBS`），**不是**数据库里那一行实际存的 `exists.func_path`。本轮 `DEFAULT_JOBS` 的 8 条已全部注册 → `func_path not in JOB_HANDLERS` **恒为 False** → **这个分支永远不执行**。

而该函数 docstring `:433` 明确写着"**存量库里已存在的未注册任务置为停用，止住每天的通知骚扰**"——**意图与代码不符**。

**后果**：存量库里 `func_path` 被写坏（不存在于 `JOB_HANDLERS`）的任务行**永远不会被自动停用** → 每天到点 `run_job` 抛 `ValueError` → `scheduler.py:141` 的失败分支给**全体 sys_admin** 推一条系统通知。这正是第二轮 P1-6 点 4 建议"把白名单校验下沉到 `init_jobs()`"想解决的问题，做了但**写错了变量**。

**修复**：把 `func_path` 改成 `exists.func_path`（并加一句注释说明为什么不能用循环变量）。1 行改动。

### P2-B　全局错误处理现在会**静默吞掉真实故障**（新增）

**位置**：`frontend/src/main.js:33-42`

```js
function isBusinessError(err) {
  if (err === undefined || err === null) return true
  if (typeof err !== 'object') {          // ← 一切非对象都算业务错误
    if (!CANCEL_REASONS.includes(err)) console.warn('[app error][非 Error 的 rejection]', err)
    return true
  }
  return err.__handled === true || err.isAxiosError === true || !!err.response
}
```

这是修 P1-9 的止血手法：把 `'cancel'` / `'close'` 归入业务错误。但实际判定规则是"**一切非对象类型**"——`CANCEL_REASONS` 只决定要不要打一行 `console.warn`，不参与判定。

**后果**：任何 `throw undefined`、`Promise.reject('boom')`、`Promise.reject()` 这类**真实故障**，现在**既不弹提示、也不挂红条**，只在控制台留一行 `console.warn` → **静默失败**。在一个后台是学生教育数据的前端系统里，"什么都不知道"比"报个错"更难排查。

**修复**：把判定收紧成显式白名单，而不是"排除一切对象"：

```js
const CANCEL_REASONS = ['cancel', 'close']
function isBusinessError(err) {
  if (err === undefined || err === null) return false
  if (typeof err === 'string') return CANCEL_REASONS.includes(err)
  if (typeof err !== 'object') return false
  return err.__handled === true || err.isAxiosError === true || !!err.response
}
```

（同时把 `utils/confirm.js` 批量迁移到那 21 处，让调用点自己吃掉 `'cancel'`，全局兜底就不需要这么宽。）

### P2-H　演示作答的内容与判分结果互相打脸（新增）

**位置**：`backend/app/services/init_db.py:733-734`（写 content + 标错）｜`:774`（`wrong_answer` 写死）

### 5.2 P1-7 的量化：70/156 到底意味着什么

**已提交产物 `audit-reports/qa/FUNCTIONAL_TEST_RESULTS.json` 的元信息**：

```json
"summary": { "total": 70, "passed": 70, "failed": 0,
             "catalog_total": 156, "unexecuted": 88 }
```

**执行构成**（kind 分布）：`write 49` + `reach 17` + `auth 2` + `public 1` + `contract 1`。
**写用例的 own_status 分布**：`400 × 32`、`422 × 8`、**`200 × 9`**。

**这 9 条 200 很重要**——它们不是"空 body 被参数校验挡下来"，而是**真的执行了业务逻辑**：

```
PUT  /system/ai-config            → 200   （空 body 就把 AI 配置覆盖了）
POST /system/ai-config/test       → 200
POST /edu/knowledge/reindex       → 200   （重建索引，重量级）
PUT  /system/notifications/read-all → 200
POST /agent/question-generator     → 200   （真的触发了题目生成）
POST /learning/review/plan         → 200
POST /learning/notes               → 200
POST /learning/goals               → 200
```

**但 88 条仍不执行**，排除理由的分布是：

| 理由 | 条数 | 评价 |
|---|---|---|
| `ui 类用例：无接口自动化，需人工/浏览器验证` | 43 | **合理**——纯 UI 场景，接口层测不了 |
| `manual 类用例：无接口自动化` | 1 | 合理 |
| **`路径含 {} 占位符：需先构造合法实体 id`** | **41** | **不合理**——这是可自动化的：按依赖顺序先 POST 建实体拿 id，再打 PUT/DELETE。**而且这批恰好是破坏性最高的路径**：`DELETE /system/users/{id}`、`PUT /system/roles/{id}`、`PUT /system/users/{id}`、`POST /jobs/{id}/run`、`POST /grading/submissions/{id}/grade`、`POST /task/tasks/{id}`… |
| **`角色 public 无独立登录令牌`** | **3** | **不合理**——public 端点本来就不需要令牌就能打（`/auth/captcha`、`/edu/classes/public`、`/system/version`），恰恰是最该被回归覆盖的一组 |

**两个必须指出的口径问题**：

1. **CI 不因"未执行"而红**：`functional-test.yml:188-195` 只判 `summary.failed > 0`。runner 虽然新增了 `unexecuted` 清单与理由（**这一步做得好——它把上一轮"138 条沉默的用例"变成了可见事实**），但**没把它接进判定**：44 条 api 用例永远不跑，CI 依然绿灯。
2. **自检口径与筛选口径同源**：`functional_runner.py:352-357` 的 `expected_ids` 定义为"api 类 + 无占位符 + 可登录角色"——**与筛选条件完全一致**，所以它只能防"筛选条件回退"，**永远发现不了 `{}` 那 41 条的缺口**。它是"防退化锁"，不是"覆盖率目标"。

**修复建议**：
1. runner 增加"实体创建 → 取 id → 带参调用"的**依赖编排**（已有的 POST 用例返回值正好可以喂给后续 PUT/DELETE）；
2. `public` 角色的 3 条按"无需令牌"路径纳入；
3. CI 判定加上：`unexecuted` 中 **api 类**用例数 > 0 时至少 warning，定下目标（0）后改 fail。

### 5.3 门禁的共同模式：基线只锁"不增长"，不推动"下降"

本轮新增/改动的三道门禁都是同一个范式：

| 门禁 | 基线 | 推动下降的机制 |
|---|---|---|
| `check_schema_bodies.py` | `BASELINE = 98` | ❌ 无（注释说"每迁移一处把 BASELINE 减 1"——**靠人记得改**） |
| `check_migration_columns.py` | `migration_baseline.json`（手工快照） | ❌ 无（`--init` 会把新列吸收进基线 → 门禁重新变绿） |
| `check_api_sql.py` | 384 | ❌ 无 |

这与上一轮 P1-3 批评的"单向门禁"是**同一类病**：门禁保证"不会变坏"，但**不保证"会变好"**。上一轮把它称为"方向性假绿"，这一轮它被推广成了全部门禁的统一范式——**这本身是个值得警惕的模式**。

**建议**：给这三道门禁各加一个"目标值"（比如 `check_schema_bodies` 的 TARGET=60），CI 在 `total <= TARGET` 时也绿，但当 `total > TARGET` 时**主动提示还差多少**，并在 PR 里输出"本 PR 是否让基线下降"的结论。至少要能看出"有没有在往正确的方向走"。
